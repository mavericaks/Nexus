4. Priority A — AI/RAG benchmark
Measure end-to-end AI ticket-triage latency for a representative set of tickets.
Measure retrieval latency separately if the code makes retrieval timing observable.
Record number of tickets tested.
Record successful AI responses, failures/timeouts, and auto-resolution decisions.
Record the confidence threshold used (currently the application logic uses a defined confidence threshold).
If possible, compare retrieval with and without the vector-search path only when the comparison is technically meaningful.
Useful final evidence could look like: 'N tickets, median triage latency X ms, p95 Y ms, Z% successful responses.' Do not claim model accuracy unless you have a labeled evaluation dataset.
5. Priority B — concurrency/scalability test
Determine how Nexus behaves as concurrent traffic increases. Test approximately 10 → 25 → 50 → 100 concurrent clients (reduce the levels if the machine cannot support them).
Record requests/sec at each level.
Record p95/p99 latency.
Record HTTP error/timeout rate.
Record CPU and memory usage if practical.
Identify the point where latency or error rate degrades materially.
The result we want is not 'supports 100 users' unless the test actually demonstrates that. A defensible statement is more like: 'At 100 concurrent requests, sustained X req/s with Y ms p95 latency and Z% errors.'
6. Priority B — database/vector-search benchmark
Measure representative PostgreSQL query latency for ticket retrieval/listing.
Measure pgvector semantic-search latency for the configured embedding dimension and index.
Record query count, dataset size, average latency and p95 latency.
If the dataset is too small for a meaningful benchmark, explicitly record the dataset size rather than implying production-scale performance.
7. Priority B — resilience/failure tests
Nexus already contains resilience mechanisms. Demonstrate that they actually behave as intended.
Redis unavailable: observe rate limiting/cache behavior and application response.
Kafka unavailable: observe event publication failure/retry behavior.
Notification service unavailable: verify circuit breaker/retry/fallback behavior.
Database temporarily unavailable: observe application behavior and recovery.
If practical, introduce one failure at a time and restore the dependency.
Record: failure injected, expected behavior, observed behavior, recovery time, and whether requests were lost or returned errors.

Record ArchUnit results separately if available.
Record Testcontainers/integration test results separately if available.
Capture the exact CI run URL/commit if GitHub Actions runs the suite.

10. What NOT to do
Do not invent a production-scale claim from a tiny local test.
Do not report a single best-case latency without stating the load.
Do not claim accuracy without labeled ground truth.
Do not compare two systems unless both were tested under equivalent conditions.
Do not benchmark only a trivial health endpoint and call it application performance.
Do not hide failed or unstable runs; record them.
Do not round results aggressively. Keep raw measurements and calculate the resume number from them.
